# 학기 전체 날짜별 시간표 전환 계획

> 작성일: 2026-09-28
> 상태: 계획 작성 중 — 구현 미착수
> 작업 범위: 현재는 이 계획 문서 작성·보완만 진행한다.
> 관련 과거 기록: [시간표 다중화 & 교사별 계획서 설계](multi_timetable_teacher_profiles.md), 특히 §10 날짜 기반 구조 전환

구현 단계·코드 경계·완료 조건은 [코드 구현 계획](daily_timetable_implementation_plan.md)에 정리한다.
작업 중단·재개 상태는 [AI 인수인계](daily_timetable_handoff.md)를 기준으로 확인한다.

## 1. 변경 목적

엑셀 시간표를 가져올 때 선택한 학기의 전체 날짜에 수업을 생성하고 저장한다.
전체 시간표, 개인 시간표, 교체 검증, 계획서 출력에서 같은 날짜별 데이터를 사용한다.

사용자가 주를 바꾸면 해당 날짜의 실제 수업 배치가 표시되어야 한다.
서로 다른 주 사이에서 교체한 수업도 출발·도착 날짜가 속한 양쪽 주에 반영되어야 한다.

## 2. 사용자와 확정한 사항

| 항목 | 확정 내용 |
|---|---|
| 생성 시점 | 엑셀 시간표를 가져올 때 학기 전체를 날짜별로 생성·저장 |
| 1학기 기본값 | 해당 연도 3월 1일~7월 31일, 양 끝 날짜 포함 |
| 2학기 기본값 | 해당 연도 8월 1일~다음 연도 1월 31일, 양 끝 날짜 포함 |
| 기간 변경 | `준비 > 기타 설정`에서 시작·종료일 수정, `반영` 버튼으로 명시적으로 적용 |
| 기존 저장 파일 | 호환·자동 변환을 구현 범위에서 제외 |
| 운영 방식 | 한 PC에서 여러 교사의 시간표 관리. 교사 선택 후 작업하며 같은 시간표의 배치·교체 결과는 공통으로 관리 |
| 이번 범위 밖 | 로그인 계정, 공통 서버, 여러 PC 동시 수정·동기화 |
| 현재 작업 | 계획 문서 작성만 진행. 코드 변경은 진행하지 않음 |

예: 2026학년도 1학기는 2026-03-01~2026-07-31,
2026학년도 2학기는 2026-08-01~2027-01-31이다.
2학기의 학년도는 시작 연도로 표시한다.

기존 저장 형식의 호환 제외는 기존 파일을 자동 삭제한다는 뜻이 아니다.
새 구조에서는 엑셀을 다시 등록해 사용하며, 기존 파일의 보관·정리 정책은 별도로 정한다.
엑셀 입력 형식 지원과 앱 내부 저장 파일 호환성은 서로 다른 문제다.

## 3. 현재 문제와 코드 확인 결과

사용자 보고: 주를 이동해도 전체 시간표에 이전 시간표가 남아 있다.
첨부 화면에서는 상단에 11월 1주와 2026-11-02~11-06이 표시되지만,
표 헤더는 9/30~10/2 날짜를 표시한다.

아래는 당시 현재 소스와 화면을 대조한 결과다. 실제 앱을 조작해 재현한 결과는 아니다.

| 문제 | 확인한 동작 | 주요 확인 위치 |
|---|---|---|
| 주 변경 후 날짜 헤더 불일치 | 주 변경 콜백에 헤더 재생성이 연결되지 않으며 헤더 비교는 날짜보다 열 구조를 기준으로 함 | `lib/ui/screens/exchange_screen/widgets/timetable_tab_content.dart`, `lib/ui/screens/exchange_screen/managers/grid_header_manager.dart` |
| 교체 결과 표시의 조건부 갱신 | 교체 보기 모드가 활성화된 경우에만 해당 주의 결과를 재합성 | `lib/providers/exchange_view_provider.dart` |
| 교체 날짜 선택 제한 | 출발·도착 날짜 모두 현재 선택한 주의 월요일과 요일로 계산 | `lib/ui/widgets/timetable_grid/exchange_executor.dart` |
| 다른 주 사이 교체 반영 한계 | 결강일 기준 주의 이벤트를 선택하고 교사·요일·교시 좌표로 수업 이동 | `lib/utils/resolved_week.dart`, `lib/models/exchange_history_item.dart` |

현재도 결강일·보강일은 저장한다. 그러나 이동 계산의 좌표에는 실제 날짜가 없고,
결강일이 속한 주를 기준으로 처리하므로 날짜 필드만으로 다른 주 사이 교체가 완성되지는 않는다.

저장 방식 변경과 함께 화면 갱신, 경로 탐색, 충돌 검증, 출력 경로를 연결해야 한다.

## 4. 엑셀 불러오기 흐름 — 제안

1. 엑셀 파일을 선택하고 읽을 수 있는 형식인지 확인한다.
2. 시간표 이름, 학년도, 1·2학기를 지정한다. 학년도·학기는 필수다.
3. 선택한 학기를 기준으로 기본 시작일·종료일을 계산한다. 준비 > 기타 설정에서 적용한 기간 설정이 있으면 해당 설정을 사용한다.
4. 엑셀의 교사·요일·교시·학급·과목을 분석하고 잘못된 값과 중복을 확인한다.
5. 기간 내 각 날짜에 해당 요일의 수업과 빈 교시를 생성한다.
6. 생성 기간, 교사 수, 수업 수와 휴일 처리 방식을 미리 보여준다.
7. 등록 확정 시 시간표 정보, 날짜별 데이터, 최초 배치를 함께 저장한다.
8. 저장 성공 후 새 시간표를 활성화하고 기간 안의 주를 표시한다.

파일 선택·학기 선택·미리보기에서 취소하거나 저장이 실패하면 기존 활성 시간표는 유지한다.
현재 불러오기 경로는 등록 전에 저장과 화면 적용을 수행하므로 이 순서를 함께 수정해야 한다.

### 4.1 학기 기간 설정과 반영

사용자 확정: 3~7월, 8~다음 해 1월은 변경 불가능한 제한이 아니라 초기 기본값이다.
`준비 > 기타 설정`에서 날짜를 바꿀 수 있으며 `반영` 버튼을 눌러 적용한다.

아래 세부 동작은 구현 권장안이다.

- 편집 대상 학년도·학기·시간표 이름과 현재 적용 기간을 화면에 명시한다. 다른 시간표를 일괄 변경하지 않는다.
- 아직 등록하지 않은 학기는 설정한 기간을 신규 등록에 사용하고, 등록된 시간표는 해당 시간표의 기간과 날짜별 데이터를 함께 반영한다.
- 입력만으로 저장·재생성하지 않는다. 편집 중인 값과 적용된 값을 분리한다.
- `기본값으로 복원`은 입력값만 되돌리고, 실제 적용은 `반영`으로 수행한다.
- 반영 전에 추가·제외 날짜와 영향받는 교체 건수를 표시한다. 시작일 역전 등 잘못된 범위는 거부한다.
- 기간 확장 시 새 날짜만 최초 엑셀 자료를 기준으로 생성한다. 기존 수업 ID·수정 배치·휴업일·교체 이력을 덮어쓰지 않는다.
- 기간 축소 시 제외되는 날짜의 자료는 보관하고 활성 조회 범위에서 제외하는 방식을 추천한다. 재확장 시 기존 자료를 재사용한다.
- 제외 날짜에 교체 이력이 있거나 교체가 범위 경계를 가로지르면 충돌 목록을 제시하고 반영을 중단하는 방식을 추천한다. 자동 삭제·자동 취소는 하지 않는다.
- 기간 설정과 데이터 조정은 한 트랜잭션으로 처리하며, 실패하면 이전 상태를 유지한다.
- 성공 후 전체·개인 시간표·주차 범위·출력 데이터를 갱신한다. 선택 주가 범위 밖이면 유효한 주로 이동한다.

구체적인 반영 구현·테스트는 [코드 구현 계획의 P3a](daily_timetable_implementation_plan.md#p3a-준비--기타-설정의-학기-기간-반영)를 따른다.

### 4.2 생성 예시

엑셀의 `김교사 / 월요일 / 1교시 / 1-1반 / 수학`을
2026학년도 2학기로 등록하면 기간 안의 모든 월요일에 독립적인 수업을 생성한다.

| 날짜 | 교사 | 교시 | 학급 | 과목 |
|---|---|---|---|---|
| 2026-09-28 | 김교사 | 1 | 1-1 | 수학 |
| 2026-10-05 | 김교사 | 1 | 1-1 | 수학 |
| 2026-10-12 | 김교사 | 1 | 1-1 | 수학 |

각 날짜의 수업은 고유 ID를 가진다. 한 날짜의 수업 변경이 다른 날짜의 수업에 전파되면 안 된다.

### 4.3 날짜와 운영일 처리

- 학기 전체 달력 날짜를 관리하되, 수업 생성은 엑셀에 정의된 요일·교시를 기준으로 한다.
- 빈 교시도 교체 대상이나 이동 가능 시간으로 조회할 수 있어야 한다.
- 월말·연말을 넘는 날짜를 정상 처리한다. 학교 날짜는 시간대 변환으로 하루가 바뀌지 않는 날짜 전용 값으로 관리한다.
- 공휴일·방학·재량휴업일 처리 정책은 아직 미확정이다. 임의로 추정해 제외하지 않는다.
- 학기 범위 밖의 날짜에 기본 주간 시간표가 반복 표시되지 않도록 한다.
- 초기 표시 주는 오늘이 학기 안이면 이번 주, 아니면 학기의 첫 운영일이 포함된 주로 하는 안을 제안한다.

## 5. 날짜별 저장 구조 — 제안

| 데이터 | 주요 내용 | 용도 |
|---|---|---|
| 시간표 정보 | 시간표 ID, 이름, 학년도, 학기, 시작·종료일, 원본 파일 정보 | 학기별 독립 관리 |
| 날짜별 운영 교시 | 시간표 ID, 날짜, 교시, 운영 여부 | 빈 시간 조회와 휴업일 관리 |
| 날짜별 수업 | 수업 ID, 시간표 ID, 날짜, 교시, 교사, 학급, 과목 | 해당 날짜의 현재 수업 배치 |
| 최초 배치 | 가져온 원본과 생성 직후 날짜별 배치 | 원본 비교와 초기화 기준 |
| 교체 이력 | 교체 ID, 유형, 관련 수업 ID, 변경 전후 배치, 실행·취소 정보 | 설명, 추적, 되돌리기 |
| 교체불가 정보 | 반복 규칙 또는 특정 날짜·교사·교시, 사유 | 날짜별 교체 검증 |

### 5.1 저장소 선정

한 PC 운영에 맞춰 로컬 SQLite를 사용하는 계획으로 진행한다. 날짜마다 별도 파일을 만드는 대신 날짜 조건으로 조회하고,
여러 날짜의 수업 변경과 이력 저장을 하나의 트랜잭션으로 처리하기 위함이다.

사용할 Flutter 패키지, 대상 플랫폼의 배포 방식과 예상 학기 데이터 크기는 구현 전에 확인한다.
저장·조회 계층은 화면에서 분리하되, 이번 단계에서 서버 연결이나 동기화는 구현하지 않는다.

### 5.2 데이터 일관성 원칙

- 현재 수업 배치를 화면·검증·출력의 공통 조회 대상으로 삼는다.
- 교사 선택은 조회·작업 대상을 바꾸는 것이며 교사별로 공통 시간표를 복제하지 않는다.
- 셀 주소는 시간표 ID·실제 날짜·교사 ID·교시로 식별한다. 사용자 계정은 셀 키에 포함하지 않는다.
- 최초 배치는 보존하고 현재 배치에 교체를 반영한다.
- 교체 이력은 현재 배치와 같은 트랜잭션에서 기록한다. 화면에서 이력을 다시 적용해 교체가 중복 반영되지 않도록 한다.
- 수업이 이동해도 수업 ID는 유지한다. 교사 변경을 포함하는 보강은 별도 의미를 명확히 정의한다.
- 같은 엑셀을 다른 학년도·학기로 등록할 수 있도록 저장 키를 파일 내용 해시만으로 정하지 않는다.
- 같은 파일·같은 학기를 다시 등록할 때 새 등록과 기존 시간표 갱신 중 어떤 동작을 할지는 별도 결정한다.
- 학기 중 새 원본을 적용하는 기능은 필요 여부 확인 후 설계한다.

## 6. 화면 표시 변경 — 제안

### 6.1 전체 시간표

- 선택한 주의 실제 날짜 범위를 조회해 표시한다.
- 상단 기간, 요일별 날짜 헤더, 수업 내용, 교체 건수는 같은 선택 상태로 갱신한다.
- 기본 화면은 교체가 반영된 현재 배치를 보여주고 원본 비교 모드를 별도로 제공하는 안을 제안한다.
- 주를 바꿀 때 기존 선택 수업·추천 경로·화살표가 잘못 남지 않게 한다.
- 다른 주 교체를 진행 중인 경우에는 고정한 출발 수업과 일반 화면 선택 상태를 구분한다.
- 부분 주에서는 학기 밖 날짜를 비활성 표시한다.

### 6.2 다른 주에 이어지는 교체 표시

예: 10/2 수업과 10/6 수업을 교체한다.

- 10/2가 포함된 주에는 10/2의 변경 결과를 표시한다.
- 10/6이 포함된 주에는 10/6의 변경 결과를 표시한다.
- 양쪽 셀에 공통 교체 번호와 상대 날짜·교시를 표시한다.
- 상대 날짜를 누르면 해당 날짜가 포함된 주로 이동한다.
- 화면 밖 셀까지 화살표를 그리는 대신 상대 날짜 링크와 상세 내역을 사용하는 안을 제안한다.
- 각 주의 건수에는 그 주에 영향을 주는 교체를 표시하되 전체 집계에서는 같은 교체 ID를 중복 집계하지 않는 안을 제안한다.

### 6.3 개인 시간표·계획서

개인 시간표도 같은 날짜별 수업을 교사 기준으로 조회한다.
계획서와 PDF 출력은 실제 교체 이력의 날짜·수업을 사용한다.
계획서에서 날짜를 바꾸는 동작이 실제 수업 배치 변경인지 단순 문서 보정인지 구분해야 한다.
실제 배치 변경이라면 동일한 충돌 검증과 트랜잭션을 거쳐야 한다.

## 7. 교체 실행과 되돌리기 — 제안

1. 실제 날짜의 출발 수업을 선택한다.
2. 상대 날짜·수업을 선택한다. 구체적인 UI는 사용자 결정이 필요하다.
3. 관련된 모든 날짜의 현재 배치를 조회한다.
4. 변경 후 상태를 기준으로 교사·학급의 동시간 충돌, 교체불가, 운영일·교시와 학기 범위를 검증한다.
5. 변경 전후 배치를 미리 보여준다.
6. 모든 관련 수업과 교체 이력을 한 번에 저장한다. 일부만 저장되는 상태는 허용하지 않는다.
7. 관련된 양쪽 주, 개인 시간표, 목록, 출력 데이터를 갱신한다.

순환·2중 교체는 대표 날짜 두 개가 아닌 각 참여 수업의 실제 날짜와 이동을 저장해야 한다.
다른 주 지원을 1:1·보강부터 시작할지 모든 유형을 함께 지원할지는 아직 미확정이다.

되돌리기도 관련된 모든 날짜를 함께 복원한다.
이후 교체가 같은 수업에 의존한다면 과거 값으로 무조건 덮어쓰면 안 된다.
후속 교체를 먼저 취소하도록 할지, 영향받는 교체를 함께 취소하도록 할지 정책을 정해야 한다.

## 8. 수정 단계와 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 미결정 정책·저장소·데이터 구조 확정 | 날짜별 수업, 원본, 교체 이력의 관계와 책임 명시 |
| 2 | 학년도·학기 선택과 학기 전체 생성 | 양 학기 전체 날짜 생성, 다음 해 1월 포함, 날짜 간 독립성 보장 |
| 3 | 등록·저장·복원·학기 전환 | 저장 실패와 취소 시 기존 상태 유지, 재시작 후 동일 데이터 복원 |
| 3a | 준비 > 기타 설정의 기간 변경·반영 | 변경 날짜만 조정, 기존 배치·이력 보존, 실패 시 이전 기간 유지 |
| 4 | 전체·개인 시간표 조회 연결 | 주 이동 시 날짜 헤더와 수업 일치, 학기 밖 수업 미생성 |
| 5 | 교체 탐색·검증·저장·취소 연결 | 날짜별 충돌 검증, 수업 배치와 이력의 원자적 변경 |
| 6 | 다른 주 교체 UI·표시·출력 | 양쪽 주에서 같은 교체 확인, 화면·계획서 결과 일치 |
| 7 | 통합 검증과 문서 갱신 | 주요 회귀 시나리오 통과, 남은 제한 기록 |

2~4단계는 기존 교체 코드가 날짜별 데이터를 잘못 해석하지 않도록 연결 상태를 확인해야 한다.
저장 파일만 날짜별로 만들고 화면·검증에서 반복 주간 데이터를 계속 사용하는 상태를 완료로 보지 않는다.

## 10. 사용자 결정이 필요한 항목

| 항목 | 제안 또는 선택지 | 상태 |
|---|---|---|
| 공휴일·방학 | 우선 전체 기간 생성 후 수업 없는 날 지정 / 최초 등록 시 제외 날짜 지정 | 미확정 |
| 다른 주 교체 UI | 출발 수업 고정 후 상대 날짜로 이동 / 두 주를 나란히 표시 | 미확정 |
| 다른 주 지원 유형 | 1:1·보강부터 / 순환·2중까지 함께 | 미확정 |
| 학기 중 원본 변경 | 적용 시작일별 원본 관리 필요 여부 | 미확정 |
| 같은 학기 재가져오기 | 별도 등록 / 기존 갱신과 교체 충돌 확인 | 미확정 |
| 후속 교체가 있는 되돌리기 | 후속 교체 먼저 취소 / 영향 범위 확인 후 함께 취소 | 미확정 |
| 기본 보기 | 교체 반영 배치를 기본으로 표시하고 원본 비교 제공 | 제안 |
| 저장소 | 한 PC용 로컬 SQLite. 패키지·배포 방식은 구현 전 확인 | 기술 세부사항 검토 필요 |

추가 기술 확인: 실제 구형 `.xls`와 `.xlsx`·`.xlsm`의 읽기 지원 여부를 구분해서 확인한다.
파일 선택창에 확장자가 있다는 것만으로 해당 형식을 읽을 수 있다고 판단하지 않는다.
