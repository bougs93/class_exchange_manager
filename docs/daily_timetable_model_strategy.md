# 날짜별 시간표 구현용 AI 모델·캐시 비용 운영 계획

작성·공식 문서 확인: 2026-09-28
상태: 권장 운영안. 실제 모델 전환·에이전트 실행은 수행하지 않음.
대상: 개발에 사용할 AI 모델. 앱에 LLM/API 기능을 추가하는 계획이 아님.

## 1. 권장안

**GPT-6 Sol을 주 구현 모델로 유지하고, 꼭 필요한 경우 GPT-6 Astra로 한 묶음의 고난도 작업을 처리한다.**
기본 추론 설정은 Sol `high`를 제안한다. 이는 이 프로젝트에 대한 작업 권장값이며 공식 기본값을 뜻하지 않는다.
기존 세션에서 다른 설정을 쓰고 있다면 설정 변경에 따른 캐시 영향도 고려하고 빈번하게 바꾸지 않는다.

공식 문서는 Sol을 복잡한 코딩·에이전트 작업용, Astra를 가장 어려운 종단간 작업용으로 설명한다.
이 프로젝트의 단계 분담은 그 특성과 비용을 고려한 판단이며 품질을 보장하는 벤치마크 결과가 아니다.
출처: [GPT-6 Sol](https://developers.openai.com/api/docs/models/gpt-6-sol), [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra).

| 작업 묶음 | 기본 권장 | 전환 조건 |
|---|---|---|
| P0~P2 조사·모델·DB | Sol 유지 | 데이터 계약·트랜잭션 설계의 모순을 해결하지 못하면 Astra 검토 |
| P3·P3a·P4 등록·설정·조회 | Sol 유지 | 주 갱신·기존 화면 통합 문제가 재현·검증 후에도 반복될 때만 검토 |
| P5~P7 교체·취소·표시·출력 | Sol 유지 | 연쇄 교체·범위 축소·원자성 문제에서 해결 진전이 없으면 Astra로 묶어서 처리 |
| P8 최종 확인 | 주 구현 모델 유지 | 별도 정합성 검토의 가치가 비용보다 높으면 Astra 검토를 한 번에 모아 진행 |

작은 UI 수정마다 저가 모델로 옮기는 방식은 기본 운영안으로 삼지 않는다.
분리 실행이 필요한 경우 명확한 입출력과 짧은 문맥으로 독립 가능한 작업인지 먼저 판단한다.
이 문서는 자동 다중 에이전트 실행 지시가 아니다.

## 2. 가격 비교 기준

공식 API Standard 요금, USD / 100만 토큰. 272K 이하 입력 구간의 표시 가격이다.

| 모델 | 일반 입력 | 캐시 읽기 | 캐시 쓰기 | 출력 |
|---|---:|---:|---:|---:|
| GPT-6 Sol | 2.00 | 0.20 | 2.50 | 10.00 |
| GPT-6 Astra | 10.00 | 1.00 | 12.50 | 50.00 |

출처: [Sol 모델 가격](https://developers.openai.com/api/docs/models/gpt-6-sol), [Astra 모델 가격](https://developers.openai.com/api/docs/models/gpt-6-astra).
장문·처리 등급·지역·도구 요금 등으로 실제 금액은 달라질 수 있으므로 착수 시 재확인한다.
이 수치를 Codex 구독 사용량이나 Orca의 실제 청구액과 동일하다고 간주하지 않는다.
계정에서 선택 가능한 모델과 과금 방식은 아직 확인하지 않았다.

## 3. 캐시를 고려한 전환 규칙

공식 캐시 문서상 재사용에는 동일한 프롬프트 앞부분이 필요하며, 모델·도구·일부 설정·압축 변화가 영향을 줄 수 있다.
같은 세션 유지도 캐시 적중을 보장하지 않는다. 다른 모델로 전환할 때는 기존 캐시가 승계된다고 예산을 잡지 않는다.
기존 모델 캐시가 즉시 삭제된다고 단정하지도 않는다. 실제 적중은 관측 가능한 사용량으로 확인한다.
출처: [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).

1. 새 구현 세션 시작 시 Sol 선택을 우선한다. 이미 긴 문맥이 쌓인 세션은 현재 단계 도중 단가만 보고 바꾸지 않는다.
2. 모델·추론 설정을 작은 작업마다 바꾸지 않는다. 단계 경계에서 필요성과 재입력 비용을 판단한다.
3. 실패한 검증과 원인이 정리된 시점에 전환한다. 무작정 더 큰 모델로 모든 과거 기록을 다시 읽히지 않는다.
4. 전환 자료는 인수인계 요약·현재 단계·관련 코드·실패 로그로 제한한다. 필요한 요구사항·데이터 계약은 빠뜨리지 않는다.
5. Astra를 사용하면 관련된 어려운 문제를 연속 처리한 뒤 종료한다. Sol↔Astra 왕복을 반복하지 않는다.
6. 긴 중단 후에는 캐시가 없을 가능성을 고려하고 짧은 인수인계부터 복구한다. 같은 모델 재개만으로 할인된다고 보고하지 않는다.
7. 문서화는 재조사 비용을 줄이는 방법이며 프롬프트 캐시 자체를 보존하는 기능은 아니다.

### 3.1 비용 판단 예시

100,000토큰의 기존 문맥이 전부 캐시 읽기로 처리된다면 Astra의 해당 입력 비용은 $0.10이다.
같은 분량을 Sol에서 새로 캐시 쓰기하면 $0.25다.
따라서 짧은 작업 하나에서는 저렴한 모델로 전환해도 문맥 재입력 비용이 더 들 수 있다.
반면 출력 10,000토큰은 이 표의 단가로 Sol $0.10, Astra $0.50이다.
긴 구현 전체에서는 출력과 재작업량까지 비교해야 한다. 이 예시는 실제 청구 예측이 아니다.

관측 가능한 API 사용량이 있으면 아래 식으로 비교한다.

```text
예상 비용 = (일반 입력 × 일반 입력 단가
            + 캐시 읽기 × 캐시 읽기 단가
            + 캐시 쓰기 × 캐시 쓰기 단가
            + 과금 출력 × 출력 단가) / 1,000,000
            + 별도 도구/처리 요금
```

입력 세 구간은 중복 합산하지 않는다. 캐시 쓰기는 일반 입력에 더하는 별도 가산 요금으로 계산하지 않는다.
모델 전환은 남은 작업 비용 절감·문제 해결 효과가 재입력·재조사 비용보다 클 때 선택한다.
전체 입력량·캐시 적중·출력량이 아직 없으므로 이번 구현 전체의 확정 비용은 제시하지 않는다.
