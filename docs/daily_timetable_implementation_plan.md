# 날짜별 시간표 코드 구현 계획

작성일: 2026-09-28
상태: 계획 작성 완료 · 코드 구현 미착수
운영 범위: 한 PC에서 여러 교사 관리

구현 모델과 캐시 비용 운영은 [AI 모델 운영 계획](daily_timetable_model_strategy.md)을 따른다.
기본 권장 모델은 GPT-6 Sol이며, 모델 선택은 앱에 AI 기능을 추가한다는 뜻이 아니다.

## 1. 시작 지점과 문서 우선순위

다른 AI 에이전트는 먼저 [진행 기록·인수인계](daily_timetable_handoff.md)를 읽는다.
그다음 이 문서의 현재 단계와 [요구사항 계획](daily_semester_timetable_plan.md)을 읽는다.

우선순위는 최신 사용자 지시 → 인수인계에 기록된 확정 결정 → 이 문서 → 요구사항 계획 → 과거 초안이다.
[주차·교체 표시 초안](multiweek_multiuser_plan.md)의 §3~§7은 미채택 또는 검토 중인 제안이며 구현 지시가 아니다.
모순이 있으면 추측하여 두 방식을 혼합하지 말고 해당 결정을 확인한다.

현재 사용자 요청은 코드 구현 **계획과 인수인계 준비**다.
후속 에이전트도 구현 지시가 있기 전에는 코드 구현을 시작하지 않는다.
이후 사용자가 구현을 지시하면 합의된 범위의 단계별 작업은 매번 허락을 다시 묻지 않고 진행한다.
제품 정책 미결정 사항은 해당 단계에 들어가기 전에 확인하되 독립적인 작업은 계속한다.

## 2. 확정 범위와 설계 방향

- 한 PC의 단일 앱에서 여러 교사의 수업을 관리한다. 로그인·서버·여러 PC 동기화는 제외한다.
- 엑셀 등록 시 학년도와 학기를 선택하고 학기 전체 날짜별 수업을 생성한다.
- 학기 초기 기본값: 1학기 해당 연도 3/1~7/31, 2학기 8/1~다음 연도 1/31. 양 끝 날짜 포함.
- `준비 > 기타 설정`에서 시작·종료일을 편집하고 `반영` 버튼으로 적용한다. 생성기는 상수가 아닌 적용된 기간을 사용한다.
- 같은 엑셀도 다른 학년도·학기에 독립 등록할 수 있다.
- 기존 앱 저장 파일의 자동 변환·호환은 제외한다. 기존 파일을 자동 삭제하지 않는다.
- 로컬 SQLite를 저장소로 계획한다. 구체적 패키지·드라이버는 지원 플랫폼과 배포를 확인한 뒤 P0에서 선정한다.
- 원본 스냅샷, 현재 날짜별 배치, 교체 이력을 분리한다. 화면과 검증은 같은 현재 배치를 사용한다.
- 주는 조회·표시 단위다. 수업의 식별·이동 단위는 실제 날짜다.
- 원본+이벤트를 매 화면에서 재적용하지 않는다. 현재 배치가 이미 변경된 뒤 이력을 다시 적용하면 중복 교체가 된다.
- UI와 저장소를 분리하되 미래 서버 기능은 미리 만들지 않는다.

### 2.1 앞으로 정해야 할 제품 정책

아래 권장안은 사용자 확정과 구분하여 기록한다. 답을 받으면 인수인계의 결정 기록을 갱신한다.

| ID | 항목 | 권장안 | 결정 필요 시점 |
|---|---|---|---|
| D1 | 방학·공휴일 | 학기 전체 생성 후 수업 없는 날 지정. 일정 자동 추정 안 함 | P3 안내·P5 운영일 검증 |
| D2 | 다른 주 교체 UI | 출발 수업 고정 → 상대 날짜 선택 → 해당 주에서 상대 수업 선택 | P6 |
| D3 | 다른 주 교체 유형 | 1:1·보강을 먼저 검증하고 순환·2중으로 확장. 최종 지원 범위는 확인 | P5 시작 전 |
| D4 | 학기 중 새 엑셀 적용 | 최초 버전에서는 별도 시간표 등록. 적용일별 원본 변경은 별도 기능 | P3 |
| D5 | 같은 학기 재등록 | 새 시간표 등록으로 기존 데이터 보존. 덮어쓰기는 명시적인 갱신 기능에서만 | P3 |
| D6 | 후속 교체가 있는 되돌리기 | 후속 교체를 먼저 취소하도록 안내 | P5 |
| D7 | 기본 화면 | 교체 반영된 현재 배치를 기본 표시, 원본 비교는 별도 모드 | P4 |
| D8 | 계획서 날짜 수정 | 실제 수업 날짜 변경이면 교체 검증·저장을 거치게 함. 문서용 날짜 보정과 구분 | P7 |

이 정책들이 미결정이어도 날짜 모델·저장소 테스트 등 영향을 받지 않는 P0~P2 작업은 진행할 수 있다.

## 3. 데이터 모델 초안

정확한 타입·파일명은 P0에서 저장하되 아래 불변 조건은 지킨다.

| 모델/테이블 | 핵심 데이터 | 역할 |
|---|---|---|
| `Timetable` / `timetables` | ID, 이름, 학년도, 학기, 시작·종료일, 원본 정보, revision | 학기별 독립 데이터 범위 |
| `SemesterPeriodSetting` / `semester_period_settings` | 학년도·학기, 적용된 시작·종료일, 대상 시간표 연결 | 등록 전 설정과 등록 후 기간 반영. UI 초안은 저장값과 별개 |
| `Teacher` / `teachers` | 시간표 ID, 교사 ID, 표시 이름 | 이름 문자열만으로 수업 식별하지 않음 |
| `CalendarDay` / `calendar_days` | 시간표 ID, 실제 날짜, 운영 상태 | 학기 전체 날짜·휴업일 관리 |
| `TeachingPeriod` / `teaching_periods` | 시간표 ID, 날짜, 교시, 운영 가능 여부 | 빈 시간의 존재와 교체 가능 시간 표현 |
| `Lesson` / `lessons` | 수업 ID, 시간표 ID, 현재 날짜·교시·교사, 학급·과목 정보 | 실제 날짜별 수업 배치 |
| `ImportSnapshot` / 원본 테이블 | 원본 파일 정보, 생성 직후 수업 배치 | 변경되지 않는 원본 비교 기준 |
| `Exchange` / `exchanges` | 교체 ID, 유형, 상태, 생성 시각, 결과 revision | 여러 날짜에 걸친 교체 한 건 |
| `ExchangeChange` / `exchange_changes` | 교체 ID, 수업 ID, 변경 전·후 배치 | 설명·추적·되돌리기 |
| `BlockedSlot` / `blocked_slots` | 시간표 ID, 교사 ID, 실제 날짜 또는 반복 요일, 교시, 사유 | 교체불가 규칙 |

### 3.1 불변 조건

1. 수업 ID는 날짜·교시가 바뀌어도 유지된다. 교체 ID와 수업 ID는 다르다.
2. 셀 주소는 시간표 ID·교사 ID·실제 날짜·교시다. 사용자 ID를 넣지 않는다. 요일은 날짜에서 계산한다.
3. 날짜는 `YYYY-MM-DD` 또는 동일 의미의 날짜 전용 타입으로 보관한다. 수업 날짜에 UTC 변환을 적용하지 않는다.
4. 셀 문자열은 화면 식별용이다. 저장·비교는 구조화된 필드로 수행하고 이름의 구분자 충돌을 피한다.
5. 수업 없는 교시와 교사/학급의 수업은 구분한다. 빈 시간 선택을 위해 빈 수업 행을 무조건 생성하지 않는다.
6. 학기 밖의 날짜는 조회하더라도 교체할 수 없다. 원본 주간 시간표로 자동 채우지 않는다.
7. 교사와 학급의 동시간 중복은 최종 배치에서 검사한다. 분반·합반·공동수업이 실제 입력에 있는지 확인한 뒤 제약조건을 확정한다.
8. 반복 교체불가와 특정 날짜 교체불가를 모두 날짜별 검증에 적용한다.
9. 교체 후 배치와 이력은 같은 트랜잭션에서 저장한다. 취소·예외 시 일부 수업만 바뀌지 않는다.
10. 현재 배치와 원본 비교 화면을 구분하고, 원본 비교 상태에서는 잘못된 배치를 기준으로 교체를 확정하지 못하게 한다.

### 3.2 저장 단위와 조회

- 앱 전용 로컬 DB 하나 안에서 시간표 ID로 분리한다. 날짜별·주별·교사별 파일을 만들지 않는다.
- 날짜 범위 조회 인덱스와 교사/학급 충돌 조회 인덱스를 둔다.
- 새 DB 자체의 스키마 버전과 이후 업그레이드 정책은 필요하다. 구 JSON 호환 제외와 혼동하지 않는다.
- Import는 생성·저장 완료 후에만 활성 시간표를 전환한다.
- 기본 수업 수가 교사 80명 × 7교시 × 평일 130일인 경우 약 72,800칸이다. 이는 예시이며 실제 데이터로 성능을 측정한다.
- 최초 스냅샷은 현재 배치와 구분해 보존한다. 스냅샷을 유지한다는 이유로 현재 배치를 파일별로 복제하지 않는다.

## 4. 코드 경계와 예상 파일

아래 신규 경로는 제안이다. 실제 생성 경로가 달라지면 이 문서와 인수인계에 기록한다.
기존 경로는 이전 조사 기준이므로 구현 직전 최신 코드 그래프로 다시 확인한다.

| 경계 | 신규 파일 제안 | 주요 기존 연결 지점 |
|---|---|---|
| 날짜·학기 모델 | `lib/models/school_semester.dart`, `lib/models/lesson.dart`, `lib/models/lesson_placement.dart` | `time_slot.dart`, `exchange_node.dart`, `exchange_history_item.dart` |
| 학기 생성 | `lib/services/semester_timetable_generator.dart` | `lib/services/excel_service.dart`의 파싱 결과 |
| DB/Repository | `lib/data/timetable_database.dart`, `lib/repositories/timetable_repository.dart` | 기존 JSON 시간표 저장·레지스트리 서비스 |
| 교체 명령 | `lib/services/dated_exchange_service.dart` | 교체 실행·되돌리기·경로 검증 서비스 |
| 조회 Provider | `lib/providers/dated_timetable_provider.dart` | `selected_week_provider.dart`, `resolved_timetable_provider.dart`, `exchange_view_provider.dart` |
| 등록 UI | 학년도·학기 다이얼로그 및 import draft | `lib/ui/screens/timetable_file_screen.dart`, `exchange_operation_manager.dart` |
| 전체 시간표 | 날짜별 조회 결과를 그리드로 변환하는 어댑터 | `timetable_tab_content.dart`, `grid_header_manager.dart`, `timetable_data_source.dart` |
| 개인 시간표·계획서 | 공통 조회 결과와 교체 이력 어댑터 | 개인 시간표, 계획서 ViewModel, PDF 데이터 구성 |

### 4.1 서비스 계약 초안

```text
parseWorkbook(file) -> ParsedWeeklyTimetable
generateSemester(parsed, schoolSemester) -> ImportDraft
previewPeriodChange(timetableId, proposedRange) -> AddedDates / ExcludedDates / Conflicts
applyPeriodChange(timetableId, proposedRange, expectedRevision) -> UpdatedRevision
importSemester(draft) -> TimetableId             // 한 트랜잭션
getSchedule(timetableId, dateRange, teacherIds?) -> DatedSchedule
previewExchange(command) -> ValidatedPreview    // 날짜와 수업 ID 포함
commitExchange(command, expectedRevision) -> ExchangeId
undoExchange(exchangeId, expectedRevision) -> UpdatedRevision
```

- 순수 파싱·학기 생성은 DB/UI에 의존하지 않도록 한다.
- 커밋은 미리보기 후 발생한 변경을 revision으로 감지하고 트랜잭션 안에서 다시 검증한다.
- 한 PC에서도 비동기 저장·연속 클릭·여러 창으로 요청이 겹칠 수 있으므로 중복 실행을 방지한다.
- 확정 시 수업 배치 변경 → 이력 저장 → revision 증가를 묶고, 성공한 뒤 조회 Provider를 갱신한다.
- 교체 미리보기는 현재 배치를 변경하지 않는다.

## 5. 단계별 실행 계획

각 단계는 완료 조건과 관련 검증을 충족한 뒤 DONE으로 기록한다.
중간 작업이 남으면 IN_PROGRESS 상태와 정확한 다음 행동을 인수인계에 기록한다.
아래 체크박스는 아직 모두 미완료다. 실행 상태의 기준 문서는 인수인계의 단계 표다.

### P0. 현황 조사·설계 확정

의존: 구현 착수 지시.

- [ ] `git status`와 HEAD를 기록하고 사용자 변경 파일을 식별한다.
- [ ] AGENTS 지시와 현재 도구를 확인한다. 코드 탐색은 MCP 그래프를 우선하며, 인덱스가 없으면 생성한다. 오래된 인덱스는 coverage 확인 후 갱신/원문 확인한다.
- [ ] 파싱→저장→레지스트리→로드→전체/개인 시간표→교체→출력의 실제 연결을 조사한다.
- [ ] 교사 ID, 학급 식별, 빈 교시, 분반·합반 데이터 표현을 확인한다.
- [ ] Windows 우선으로 DB 패키지·파일 위치·네이티브 라이브러리 배포를 결정한다. 지원해야 할 다른 플랫폼을 확인한다.
- [ ] `.xls`, `.xlsx`, `.xlsm`의 실제 읽기 지원을 구분한다. 확장자 필터만 보고 지원한다고 결론내리지 않는다.
- [ ] 지원 안 되는 입력은 명확한 오류 안내 또는 별도 변환 지원으로 정책을 정한다.
- [ ] 관련 기존 테스트의 기준 결과와 사전 실패를 기록한다.

완료: 데이터 계약·패키지 선택 근거·실제 영향 파일·테스트 기준을 기록. 파일 형식 미지원이나 분반 충돌을 숨기지 않음.

### P1. 날짜 모델·학기 전체 생성

의존: P0. 제품 정책 D1~D8의 답을 기다리더라도 독립 구현 가능.

- [ ] 날짜 전용 값, 학기 범위, 수업 ID·배치 모델 작성.
- [ ] 기본 학기 범위 계산과 사용자 지정 실제 적용 범위를 분리. 생성기에 실제 범위를 전달.
- [ ] 엑셀 요일별 데이터를 실제 날짜별 독립 수업으로 생성.
- [ ] 날짜별 운영 교시 생성. 학기 밖 데이터 생성 금지.
- [ ] 원본 스냅샷과 현재 배치의 독립성 보장.
- [ ] 잘못된 요일·교사·교시와 중복 입력의 처리 규칙 적용.

검증: 1학기 양 끝, 2학기 다음 해 1/31, 연말, 부분 주, 빈 교시, 같은 요일의 다른 날짜 독립성, 입력 원본 불변성, 학기별 ID 충돌 없음.

## 7. 중단·재개 프로토콜

토큰/컨텍스트 여유가 적어지면 큰 리팩터링을 새로 시작하지 말고 현재 변경을 저장한다.
자동 압축이나 강제 종료가 올 수 있으므로 정상 종료 직전뿐 아니라 각 작은 작업 단위가 끝날 때 기록한다.

1. [인수인계](daily_timetable_handoff.md)의 현재 단계·다음 작업을 갱신한다.
2. 실제 변경 파일과 마지막 검증 명령·결과·미실행 항목을 적는다.
3. 컴파일 불가 상태라면 원인·에러·다음 수정 위치를 적는다. 완료로 표시하지 않는다.
4. 사용자 결정, 임시 코드, 남은 위험, 실행 중 프로세스와 로그 위치를 적는다.
   사용 모델·추론 설정·캐시 관측 가능 여부·모델 전환 사유도 함께 기록한다.
5. `git status --short`, `git diff --stat`, 현재 HEAD를 확인해 작업 경계를 기록한다.
6. 사용자 변경을 포함해 일괄 되돌리거나 정리하지 않는다. 커밋은 실제로 생성한 경우에만 해시를 기록한다.
7. 별도 에이전트가 자동 실행된다고 가정하지 않는다. 재개 요청 시 아래 인수인계 문서로 시작하도록 안내한다.

재개한 에이전트는 기록을 믿고 바로 다음 단계로 넘기지 말고 현재 파일·diff·검증 결과와 대조한다.
완료한 단계를 이유 없이 반복하지 않되, 파일 변경이나 실패 때문에 기록이 무효해진 경우 필요한 검증만 다시 한다.
