## 2. 확정된 방향

- 한 PC에서 여러 교사 관리. 로그인·서버·여러 PC 동시 수정 제외.
- 엑셀 등록 시 학기 전체 날짜별 수업 생성.
- 초기 기본값: 1학기 3/1~7/31, 2학기 8/1~다음 해 1/31.
- `준비 > 기타 설정`에서 시작·종료일 수정 후 `반영` 버튼으로 적용. 기본값을 변경 불가능한 상수로 구현하지 않는다.
- 로컬 SQLite 기반 계획. 패키지·배포 세부사항은 P0에서 확인.
- 교사 선택은 공통 시간표의 작업 대상 선택이다. 사용자별 시간표 복제나 사용자 포함 셀 키를 만들지 않는다.
- 원본 스냅샷·현재 배치·교체 이력 분리. 현재 배치에 교체 이력을 다시 얹지 않는다.
- 기존 저장 파일 변환·호환 제외. 기존 파일 자동 삭제는 하지 않는다.

`multiweek_multiuser_plan.md`의 주별 JSON, 사용자 포함 키, 날짜 없는 확정, 주 이동 재검증 생략은 확정 설계가 아니다.

## 4. 미결정 사항

구현 계획 §2.1의 D1~D8을 따른다. 현재 전부 제품 정책 미확정이다.
특히 다른 주 교체 UI, 지원 교체 유형, 휴업일 처리, 후속 교체 취소, 계획서 날짜 수정 의미를 임의로 확정하지 않는다.
답이 필요하지 않은 모델·저장소 준비까지 모두 막지는 않는다.

| 날짜 | 결정 ID | 사용자 답변 또는 결정 근거 | 영향 단계 |
|---|---|---|---|
| 2026-09-28 | 운영 범위 | 한 PC에서 여러 교사 관리로 사용자 확정 | 전체 |
| 2026-09-28 | 학기 기간 | 기존 기간은 기본값. 준비 > 기타 설정에서 수정하고 버튼으로 반영 | P1~P5 |

### 모델 운영 상태

- 권장: GPT-6 Sol을 주 구현 모델로 유지. 어려운 정합성 문제 또는 최종 검토에만 GPT-6 Astra 검토.
- 현재 모델을 자동 변경하거나 별도 에이전트를 생성한 상태가 아니다.
- 실제 사용 모델·요금 방식·캐시 적중량은 구현 착수 시 기록한다. 모르면 미확인으로 둔다.
- 중단 후에는 같은 모델로 재개를 우선하되 캐시가 남아 있다고 가정하지 않는다.

## 5. 발견 사항과 주의할 코드

- `ExchangeHistoryItem`은 이미 결강일·보강일을 저장한다. 날짜 개념이 전혀 없는 앱이라고 가정하지 않는다.
- `ResolvedWeek`는 결강일의 주를 골라 요일 좌표로 이동한다. 날짜별 DB 전환 후 그대로 사용하면 다른 주 교체가 잘못 적용될 수 있다.
- `refreshIfEnabled`는 교체 보기 상태에 의존한다. 표시와 검증이 서로 다른 수업을 보지 않도록 통일해야 한다.
- 헤더 비교가 열 구조 중심이며 주 변경 콜백에 헤더 갱신이 빠져 있는 경로를 이전 조사에서 확인했다.
- 파일 등록 전 저장·활성 화면 적용, 동일 파일 변경 시 초기화 흐름을 확인해야 한다. 취소만 해도 기존 자료가 바뀌면 안 된다.
- 기존 코드 그래프에서 2026-08-29의 오래된 인덱스가 반환된 적이 있다. 현재 소스와 일치하는지 coverage/freshness를 확인한다.
- 코드 발견은 MCP 그래프 우선. 부족하거나 오래된 결과는 원문 확인으로 보완하고 그 이유를 기록한다.
