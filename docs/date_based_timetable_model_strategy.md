# 날짜 기반 시간표 구현용 AI 모델·캐시 비용 운용 계획

작성일: 2026-09-29 (Claude 5 계열 공식 가격 기준)
상태: 권장 운용안. 실제 모델 전환·에이전트 실행은 수행하지 않음.
대상: 개발에 사용할 AI 모델(Claude Code). 앱에 LLM/API 기능을 추가하는 계획이 아니다.

관련: [계획서](date_based_timetable_plan.md), [단계별 실행 계획](date_based_timetable_steps.md)

과거 보관 문서 `daily_timetable_model_strategy.md`는 GPT-6 Sol/Astra 기준이며 이번 프로젝트(Claude 계열)와 무관하다.

## 1. 권장안

**Claude Sonnet 5를 주 구현 모델로 유지하고, 회귀 위험이 큰 구간에서만 Claude Opus 5로 검토·구현을 맡긴다.**

| 단계 | 기본 모델 | Opus 5 전환 조건 |
|---|---|---|
| S0 현황 조사 | Sonnet 5 | 조사만이므로 전환 불필요 |
| S1 날짜 전용 데이터 모델 | Sonnet 5 | UI·저장소 미연결, 순수 로직 — 전환 불필요 |
| S1.5 날짜표시 스위치(교체 화면) | Sonnet 5 | 위젯 트리·오버레이 레이어 설계가 꼬이면 Opus 5로 설계 검토 1회 |
| S2 SQLite 스키마·Repository | Sonnet 5 | 트랜잭션·인덱스 설계 확정 전 Opus 5로 검토 1회 권장 |
| S3~S3a 등록·기간 반영 UI | Sonnet 5 | 반복 실패 시에만 |
| **S4~S5 화면 조회·교체 로직 날짜 기반 전환** | Sonnet 5 (구현) + **Opus 5 (설계 검토)** | 지난 실패(`c4867cf`)가 발생한 구간. 착수 전 Opus 5로 설계·회귀 위험 검토를 한 번 받고, 구현은 Sonnet 5로 작게 쪼개 진행 |
| S6 다른 주 교체 UI | Sonnet 5 | S5와 동일 기준 |
| S7 계획서·PDF 출력 | Sonnet 5 | 필요 시 |
| S8 최종 통합 확인 | Sonnet 5 | 전체 회귀 결과가 모순되거나 원인 불명확할 때 Opus 5로 최종 점검 1회 |

작은 문서 수정·단순 파일마다 모델을 바꾸지 않는다. 모델 전환은 캐시를 전부 무효화하므로(§3),
전환 이득이 재입력 비용보다 클 때만, 그것도 관련 문제를 한 번에 몰아서 처리한 뒤 원래 모델로 돌아온다.

## 2. Claude 5 계열 가격 (공식 API, USD / 100만 토큰)

| 모델 | 일반 입력 | 캐시 읽기 | 캐시 쓰기(5분) | 캐시 쓰기(1시간) | 출력 |
|---|---:|---:|---:|---:|---:|
| Claude Opus 5 | 5.00 | 0.50 | 6.25 | 10.00 | 25.00 |
| Claude Sonnet 5 | 3.00 | 0.30 | 3.75 | 6.00 | 15.00 |
| Claude Haiku 4.5 | 1.00 | 0.10 | 1.25 | 2.00 | 5.00 |

캐시 읽기 = 일반 입력의 0.1배, 캐시 쓰기 = 5분 TTL 1.25배 / 1시간 TTL 2배 (Anthropic 공식 공통 배수).
Sonnet 5의 2026-08-31까지 적용된 도입 할인가($2.00/$10.00)는 오늘(2026-09-29) 기준 종료되어 위 정상가를 기준으로 삼는다.
Haiku 4.5는 참고용으로만 기재한다 — 이 프로젝트의 구현 작업에는 권장하지 않는다(복잡한 Flutter 리팩터링에는 품질 위험이 큼). 다만 매우 단순하고 독립적인 하위 작업(예: 반복적인 보일러플레이트 생성)을 별도 세션으로 분리할 때는 고려할 수 있다.

## 3. 캐시를 고려한 전환 규칙

- **모델 전환에는 캐시 이전(carry-over) 자체가 없다.** 캐시는 모델별로 분리되어 있으며, Sonnet 5 ↔ Opus 5 전환 시 이전 대화에서 쌓인 캐시를 그대로 이어받지 못한다. 전환 즉시 그 시점까지의 문맥을 캐시 쓰기 가격으로 다시 써야 한다.
- **이 세션(Claude Code)의 캐시 TTL은 기본 1시간이다.** 요금 한도 초과 등으로 상태가 바뀌면 5분으로 낮아질 수 있으나, 이는 세션이 알아서 처리하는 부분이며 작업 계획에서 별도로 추적하지 않는다.
- **작은 단계마다 모델을 바꾸지 않는다.** S4~S5처럼 정말 위험도가 높은 구간에 진입하기 직전에만 Opus 5로 전환해 설계 검토를 받고, 검토가 끝나면 다시 Sonnet 5로 돌아와 구현을 이어간다. Sonnet 5 ↔ Opus 5를 반복 왕복하지 않는다.
- **전환 시 넘길 자료를 최소화한다.** 인수인계 요약(`date_based_timetable_handoff.md`)·현재 단계 설명·관련 코드 조각·실패 로그로 제한한다. 전체 대화 이력을 그대로 복사해 새 캐시를 처음부터 쓰게 하지 않는다.
- **툴 목록·시스템 프롬프트를 세션 중간에 바꾸지 않는다.** 툴 정의 추가/삭제/모델 전환은 캐시 전체를 무효화한다. 이번 프로젝트는 Claude Code 표준 툴셋을 그대로 쓰므로 해당 없음.

### 3.1 비용 판단 예시

기존 대화 문맥 100,000토큰이 있다고 가정한다.

- **같은 모델(Sonnet 5)로 계속 진행**: 캐시 읽기로 처리되면 $0.03 (100,000 × $0.30/1M).
- **Opus 5로 전환**: 캐시가 없으므로 같은 100,000토큰을 캐시 쓰기(1시간 TTL) 가격으로 다시 써야 한다 → $1.00 (100,000 × $10.00/1M). 이후 같은 세션에서 계속 읽으면 회당 $0.05 (100,000 × $0.50/1M).
- 짧은 검토 1회만 필요하다면 재입력 비용($1.00)이 검토로 얻는 이득보다 클 수 있다. **여러 개의 얽힌 설계 문제를 한 번에 몰아 처리**해야 전환 비용이 상쇄된다 — 이것이 S4~S5에서만 전환을 권장하는 이유다.

이 수치는 참고용 계산이며 실제 청구액은 세션의 실제 입력·출력·캐시 적중 패턴에 따라 달라진다.
