# 웹 전환 작업 인계 브리핑 (AI 에이전트용)

> 이 문서는 `docs/web_conversion_plan.md`(웹 전환 계획서)를 실제로 구현할
> AI 코딩 에이전트에게 **최초 1회 프롬프트로 그대로 전달**하기 위한
> 브리핑이다. 이 문서를 읽는 모델은 이 프로젝트의 이전 대화 맥락을 전혀
> 모른다는 전제로 작성했다.

## 네가 할 일

너는 Flutter로 만든 "교사용 시간표 교체 프로그램"(`class_exchange_manager`)을
웹에서도 쓸 수 있게 만드는 작업을 맡았다. 전체 설계는 이미
`docs/web_conversion_plan.md`에 확정되어 있다. **설계를 다시 고민하지
말고, 그 문서에 적힌 대로 구현하라.** 애매하거나 문서에 없는 상황을
만나면 추측해서 진행하지 말고 사용자에게 먼저 질문하라.

## 시작하기 전에 반드시 읽을 파일

1. `CLAUDE.md` — 프로젝트 전체 아키텍처, 코딩 컨벤션(Riverpod 상태 관리
   규칙, 한국어 현지화, SnackBarHelper 사용 등). 이 프로젝트의 모든 규칙은
   여기 우선한다.
2. `docs/web_conversion_plan.md` — 웹 전환 계획서 전체. 11개 장으로
   구성되어 있고, 11장(결정 대기 사항)에 체크된 항목은 이미 확정된
   것이니 재논의하지 말 것.

## 절대 지켜야 할 제약 (계획서에서 가장 중요한 부분 요약)

- **PC/모바일 앱의 동작은 절대 바꾸지 않는다.** 파일을 조건부 import로
  분리하는 과정에서 로직 자체가 달라지면 안 된다. 분리 작업 직후에는
  반드시 `flutter build windows`(또는 안드로이드 빌드)로 회귀가 없는지
  확인한다.
- **보안보다 편의성이 우선**이라고 이미 확정되어 있다. 과도한 보안
  장치(OAuth, 2FA 등)를 임의로 추가하지 말 것. 단, 비밀번호 평문이
  비로그인 상태에서 그대로 노출되는 구조는 계획서 4장에서 이미 막아뒀으니
  그 설계(공개/비공개 문서 분리)는 그대로 따를 것.
- **공용 시간표는 SQLite 파일을 통째로 주고받지 않는다.** JSON으로
  직렬화해서 전송하고, 받는 쪽에서는 이미 열려 있는 로컬 SQLite에
  INSERT하는 방식이다 (계획서 3장). 이 부분은 과거에 "파일 통째 전송"으로
  설계했다가 기술적으로 막혀서 변경된 것이니, 다시 파일 전송 방식으로
  되돌리지 말 것.
- **작업 순서는 계획서 9장(단계별 작업 계획)을 따른다.** 특히 0단계
  (`flutter build web`로 전체 컴파일 에러 먼저 확인)를 건너뛰지 말 것 —
  이 결과에 따라 조건부 import 분리 대상 범위가 달라질 수 있다.
- 한국어 사용자 대면 텍스트/주석 컨벤션을 유지한다 (CLAUDE.md 참고).

## 아직 정해지지 않은 값 (사용자에게 물어볼 것)

계획서 11장 기준으로 아래 항목은 아직 실제 값이 없다. 구현 중 이 값이
필요한 시점에 도달하면 사용자에게 물어보고, 추측하거나 임의로 정하지
말 것:

- Firebase 프로젝트 생성 주체/계정 (결제수단 등록 가능 여부 포함)
- 마스터 ID·비밀번호 실제 값
- 관리자 비밀번호 초기값, 접속자 비밀번호 초기값
- 로그인 안내 메시지 초기 문구
- Firebase Hosting 도메인(기본 `*.web.app` 사용 여부, 커스텀 도메인 연결 여부)

(참고: 호스팅은 **Firebase Hosting**으로 확정되었다. 당초 Cloudflare
Pages(`class-swap` 프로젝트)로 진행하려 했으나 사용자 결정으로 변경되었으니,
Cloudflare 관련 설정은 더 이상 작업 대상이 아니다 — 계획서 11장 참고.)

## 작업 진행 방식 권장

- 계획서 9장의 각 단계를 끝낼 때마다 `flutter analyze`와 관련 빌드
  (`flutter build web`, 필요 시 `flutter build windows`)를 돌려 확인하고
  나서 다음 단계로 넘어갈 것.
- 한 번에 전체를 구현하려 하지 말고, 9장의 단계 단위로 끊어서 진행하고
  각 단계가 끝나면 결과를 보고할 것.
- 비가역적이거나 공유 상태에 영향을 주는 작업(Firebase 프로젝트 설정 변경,
  배포, git push 등)은 실행 전에 사용자 확인을 받을 것.
