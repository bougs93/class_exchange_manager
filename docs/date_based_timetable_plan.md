## 1. 배경 — 이전 시도와 실패

이번 재작업은 같은 목표를 유지하되, **작은 단위로 나누어 매 단계 기존 기능을 검증**하는 방식으로 진행한다.

## 2. 목표

1. 시간표의 셀 식별·이동 좌표를 요일·교시 중심의 **주 단위(week)** 기반에서 **실제 날짜(date)** 기반으로 전환한다.
2. 전환 과정 중, 그리고 전환 완료 후에도 **현재 정상 동작하는 기능은 그대로 유지**한다.
   - 1:1 교체, 순환 교체, 2중 교체
   - 전체/개인 시간표 표시, 주 이동
   - 결보강 계획서·PDF 출력
   - 그 외 `docs/current_exchange_systems.md`에 기술된 기존 기능 전반
3. 여러 주 사이의 교체(예: 이번 주 수업을 다음 주로 이동)를 날짜 기반으로 정확히 표현·검증·표시한다.

## 4. 재작업 핵심 원칙

1. **비파괴 우선**: 각 실행 단계의 완료 조건은 "신규 기능 동작"뿐 아니라 "기존 기능이 여전히 동일하게 동작"을 포함한다.
2. **작은 단위로 쪼갠 커밋**: 한 커밋·한 단계에서 바꾸는 파일 수를 최소화한다. 특히 화면(UI) 연결과 기존 저장 경로 교체는 여러 단계로 나눈다.
3. **병행 경로 유지**: 날짜 기반 모델·저장소를 기존 주 단위 구조 옆에 추가하고, 새 구조가 검증되기 전까지 기존 화면·로직은 기존 경로를 계속 사용한다. 검증 전에 기존 코드를 들어내지 않는다.
4. **매 단계 회귀 검증**: 각 단계 완료 조건에 `flutter analyze`, 관련 `flutter test`, 그리고 최소한 수동으로 핵심 시나리오(1:1 교체, 주 이동, 개인 시간표, PDF 출력 확인) 점검을 포함한다.
5. **단계 분할은 이 문서와 `date_based_timetable_steps.md`의 새 기준을 따른다.** 삭제된 과거 문서의 세부 데이터 모델·서비스 계약 초안은 재사용하지 않고, `date_based_timetable_steps.md`에서 단계별로 다시 설계한다.
6. **미결정 정책은 임의로 확정하지 않는다**: 공휴일·방학 처리, 다른 주 교체 UI, 순환/2중의 다른 주 지원 범위, 계획서 날짜 수정의 의미 등은 과거 문서의 D1~D8 항목과 동일하게 미결정 상태로 유지하고, 해당 단계 진입 전에 사용자에게 확인한다.

## 5. 화면 표시 사양 (확정, 2026-09-29)

아래 주차 표시 스위치 사양은 2026-09-29 사용자가 직접 확정한 내용이다.

### 5.1 기준 동작 (현재 기능, 유지 대상)

1. **"교체" 페이지**: 날짜를 선택하지 않은 상태로 교체를 실행한다 (요일·교시 기준).
2. **"계획서" 페이지**: 교체 실행 후, 이 페이지에서 날짜를 선택해 확정한다.

### 5.2 신규 요구사항

3. **"교체" 페이지에 "날짜표시" 스위치를 추가**한다.
4. **"계획서"에서 날짜 선택이 확정되면**, "교체" 페이지의 표시가 아래처럼 갈라진다.

| 날짜표시 스위치 | 표시 방식 |
|---|---|
| **비활성화 (OFF)** | 기존과 같은 방식(요일만, 날짜 없음)으로 표시하되, 교체된 칸에 **오버레이로 날짜를 추가 표시**한다 |
| **활성화 (ON)** | 상단에 주차를 표시하고, 요일 헤더에 `월(9.29)`처럼 날짜를 함께 표시한다. 교체된 실제 시간은 `🔲 빠진 수업 / ○ 맡은 수업` 형태로 표시한다 (빠진 수업 = 원본에서 빠진 칸, 맡은 수업 = 새로 맡게 된 칸) |

신규 `showWeekHeaderProvider`(가칭) 스위치로 두 표시 모드를 전환하는 방식을 사용한다.

이 표시 사양은 S6(다른 주 교체 UI·표시) 및 D2·D7 정책과 연결된다. 구현 시점의 세부 위젯 연결(`SimplifiedTimetableCell`, `TimetableDataSource._createDataCellState` 등)은 `date_based_timetable_steps.md`에서 해당 단계 착수 시 재확인한다.
